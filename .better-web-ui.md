# PPI Ishikawa — Design Context

This file is the canonical UI/UX context for future design work.

## Product

PPI Ishikawa is the digital home for Indonesian students, families, and alumni in Ishikawa Prefecture, Japan. It combines a public information portal with a members-only area.

The public site helps users orient themselves, find practical information, compare campuses, discover scholarships/career resources, and understand PPI Ishikawa. The member area supports membership, events, directory, organization, documents, certificates, mentoring, volunteering, and related community workflows.

## Primary audiences

1. Prospective/new students preparing to move to Ishikawa.
2. Current Indonesian students across Ishikawa institutions.
3. Students living with spouses/children.
4. Alumni.
5. Committee members administering the organization.

## Primary UX outcomes

- A user should know where to start within a few seconds.
- Information-heavy pages should remain scannable instead of becoming walls of cards.
- The next action should be obvious without making every action visually primary.
- Public information and member workflows should feel like one product family.
- Mobile should be treated as a primary usage context, not a reduced desktop layout.
- Official-source links and status information should remain trustworthy and legible.

## Brand personality

Contemporary, warm, useful, trustworthy, student-centered, and quietly distinctive.

Avoid looking like:
- a generic startup landing page
- a government portal
- an over-decorated student organization site
- an AI-generated card grid
- a dashboard where every surface competes for attention

## Core visual identity

- Primary typeface: Plus Jakarta Sans Variable.
- Japanese fallback: Hiragino Sans, Yu Gothic, Meiryo.
- Typography is long-lived core identity.
- Period palette and active period live in `src/data/brand.ts`.
- Current visual language uses restrained red/teal accents, warm-neutral surfaces, rounded geometry, and simple line icons.

## Design principles

### 1. Task before decoration
Design the task a user is trying to complete first. Navigation, cards, badges, and decorative surfaces must support the task rather than become the interface itself.

### 2. Hierarchy must work in grayscale
Priority should be communicated through scale, spacing, weight, grouping, and position. Color is reinforcement, not the only differentiator.

### 3. Fewer surfaces, stronger grouping
Do not put every content group inside a bordered white card. Prefer whitespace, section backgrounds, dividers, and typographic grouping. Reserve elevated/outlined cards for independently actionable objects.

### 4. One clear action hierarchy
A viewport should have a recognisable primary action, secondary actions, and tertiary links. Repeated list-item actions should not all look like primary CTAs.

### 5. Rhythm over uniform spacing
Related elements stay tight. Separate conceptual groups more generously. Avoid giving every section the same padding and every card the same internal spacing.

### 6. Mobile clarity
Touch targets, filters, navigation, data density, and long headings must remain comfortable around 360–430 px widths.

### 7. System before exceptions
Use semantic color and typography tokens, constrained radius/spacing patterns, and reusable interaction patterns. Avoid one-off visual tweaks unless there is a clear UX reason.

### 8. Restraint
Use shadows, hover lift, accent backgrounds, pills, uppercase labels, and large radii selectively. Personality comes from typography, color temperature, composition, and image treatment—not from stacking effects.

## Current component roles

- Hero / feature panel: rare, high-emphasis entry point.
- Standard card: independently actionable object.
- Soft group: related supporting information that does not need a strong boundary.
- List row: repeated resource/result item.
- Primary button: one main next action.
- Secondary button: alternative action.
- Text action: repeated or tertiary action.
- Eyebrow: short context label; not required above every heading.

## Technical constraints

- Astro 7
- Tailwind CSS 4
- GitHub Pages deployment
- Supabase-backed Member Area
- Light/dark mode
- Semantic brand tokens and automated theme guard
- Avoid adding large client-side dependencies only for visual effects
- Preserve reduced-motion support and keyboard focus visibility

## Current UI/UX focus

Do not add content during UI/UX refinement unless content is required to fix an interaction defect. Current work should focus on hierarchy, arrangement, surfaces, actions, responsiveness, accessibility, and polish.
